# Участие в разработке

Документация проекта: [docs/README.md](docs/README.md). Текущая линия — **3.0.x** (см. [CHANGELOG.md](CHANGELOG.md), [docs/ROADMAP.md](docs/ROADMAP.md#ветка-30--глубинная-диагностика)).

## Версионирование (SemVer)

Версия в `package.json` следует [Semantic Versioning 2.0.0](https://semver.org/lang/ru/): **`MAJOR.MINOR.PATCH`**.

**Общее правило:** мажор — «ломаем ожидания пользователя или оператора»; минор — «добавляем или заметно улучшаем, старые сценарии работают»; патч — «чиним и шлифуем без новых сценариев».

### PATCH (например 1.2.3 → 1.2.4)

- Исправления багов, регрессий, краёвых случаев.
- Исправления уязвимостей без смены контракта для пользователя.
- Небольшие правки текстов/промптов, если продукт для пользователя тот же.
- Внутренние рефакторинги без изменения поведения бота.

### MINOR (например 1.2.0 → 1.3.0)

- Новые команды, кнопки, типы раскладов, режимы — при условии, что **старый** UX не убран и не сломан.
- Новые **необязательные** переменные окружения или опции с разумными значениями по умолчанию.
- Улучшения UX (подписи к фото, разбиение длинных сообщений и т.д.) без ломания прежнего потока.
- Усиление валидации, таймауты, логи — если деплой не требует обязательных новых шагов (кроме редких случаев: если новая проверка отсекает заведомо неверный `.env`, это всё равно часто **minor**, а не major).

### MAJOR (например 1.x.x → 2.0.0)

- Удаление или несовместимая смена команд/колбэков/смысла кнопок для пользователя.
- Смена формата сообщений в Telegram так, что клиенты/привычки ломаются (например, резкая смена `parse_mode` и контракта разметки без переходного периода).
- Требования к оператору: **обязательные** новые секреты/шаги без обратной совместимости, снятие поддерживаемой версии Node.js, смена модели деплоя так, что старый runbook не работает.
- Появление персистентности (БД и т.п.) с **обязательной** миграцией данных между мажорными версиями.

Git-теги релизов: **`v` + версия**, например `v1.2.3` (число совпадает с `package.json` в поле `version` **без** префикса `v`). Рекомендуется **аннотированный** тег: `git tag -a vX.Y.Z -m "краткое описание релиза"`.

## Релиз (пошагово)

1. Убедитесь, что `main` зелёный в CI.
2. В `CHANGELOG.md` перенесите пункты из **`[Unreleased]`** в новый блок **`[X.Y.Z] — YYYY-MM-DD`**.
3. Обновите **`version`** в `package.json` (без префикса `v`).
4. Перепишите **`whatsNewHtml()`** в `src/releaseNotes.ts`, если релиз заметный для пользователя (см. `.cursor/rules/release-notes.mdc`).
5. Коммит (например: `chore: release v1.2.3`).
6. Тег: `git tag -a vX.Y.Z -m "vodovorot vX.Y.Z"` (или эквивалент) и `git push origin main && git push origin vX.Y.Z`.
7. Workflow **Release** (`.github/workflows/release.yml`) создаст [GitHub Release](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases) с автогенерацией заметок по коммитам; при необходимости отредактируйте текст релиза вручную и сверьте с `CHANGELOG.md`.

Публикация в npm для этого проекта не предполагается (`private: true`).

## Сообщения коммитов

Формат — **[Conventional Commits](https://www.conventionalcommits.org/)** на **английском** (так проще читать историю и автогенерацию релизов).

**Структура:** `<type>(<scope>): <краткое описание в повелительном наклонении>`

Пустая строка, затем **тело** (опционально): маркированный список или абзацы с деталями.

**Частые `type`:**

| Тип        | Когда использовать                                  |
| ---------- | --------------------------------------------------- |
| `feat`     | новая возможность для пользователя бота / оператора |
| `fix`      | исправление бага                                    |
| `docs`     | только документация                                 |
| `chore`    | рутина (зависимости, конфиг CI без смены поведения) |
| `ci`       | workflow GitHub Actions                             |
| `test`     | тесты                                               |
| `refactor` | рефакторинг без смены поведения                     |

**`scope`** — короткая зона кода (необязательно): `deploy`, `bot`, `ai`, `deck` и т.п.

**Примеры:**

```text
fix(bot): handle empty AI response without crashing

feat(deploy): add DigitalOcean SSH deploy workflow after CI
```

**Не добавляйте** в конец сообщения служебные хвосты вроде `Made-with: Cursor` — они засоряют историю.

Если Cursor (или другой инструмент) **всё равно дописывает** такую строку через `prepare-commit-msg`, сделайте коммит из терминала с пустым каталогом хуков (подставьте путь к существующей **пустой** папке):

```bash
git -c core.hooksPath=/path/to/empty-dir commit …
```

Либо отключите автоподпись в настройках Cursor для интеграции с Git.

## Процесс правок

1. Ветка от `main`: `feature/…`, `fix/…` или `chore/…`.
2. **Прямой push в `main` отключён** (branch protection): изменения только через **Pull Request** и merge после зелёного CI.
3. В описании PR — **что сделано** и **`Closes #номер`** при привязке к issue.
4. CI (lint, **test:coverage**, сборка, проверка форматирования) должны быть зелёными.

Подробнее о защите ветки и настройках репозитория: [docs/DEV-PROCESS.md](docs/DEV-PROCESS.md).

## TDD и покрытие

- **Красный → зелёный:** для багов в `src/` (кроме `handlers/`, `bot.ts`) сначала тест, потом правка.
- **CI** гоняет `npm run test:coverage` с порогами из `vitest.config.ts`. Из coverage исключены хендлеры, `bot.ts`, доставка в Telegram и сырой OpenRouter — см. `COVERAGE_EXCLUDE` в `vitest.config.ts`.
- **Приоритет тестов:** колода и сессии deep, композит фото (чёрный фон + альфа карт), парсинг `РЕЗЮМЕ:`, тексты `botCopy` / caption, репозиторий SQLite.
- **Не обязательно:** полный mock Telegraf; при новом сценарии в хендлере — вынеси решение в функцию под `src/` и покрой её.

## Локальные проверки

После `npm ci` активируется **pre-commit** (Husky): на файлах в индексе — `eslint --fix` и Prettier; затем те же **`npm run lint`** и **`npm run format:check`**, что и в CI. Коммит не пройдёт, пока линтер или форматирование по репозиторию красные.

Ручной прогон (как в CI, без коммита):

```bash
npm run lint:fix
npm run format
npm run lint
npm run format:check
npm run test:coverage
npm run build
```

Обойти хук (редко, осознанно): `git commit --no-verify` или `git -c core.hooksPath=/path/to/empty-dir commit …` — см. выше про Cursor.
