# Деплой

Бот — долгоживущий процесс (`npm start`), удобно крутить в контейнере или на VPS. Ниже: **Docker**, **Railway**, опционально **деплой из GitHub Actions**.

**Личные сообщения:** бот рассчитан на работу **только в private-чате** с пользователем. В группах и каналах обновления **не обрабатываются** (ответов нет).

**Профиль в BotFather (About, Description, Privacy Policy):** см. [docs/BOTFATHER.md](BOTFATHER.md).

**Команды в BotFather (@BotFather → Edit Bot → Edit Commands)** — выставить вручную:

| Команда | Подсказка (пример) |
| ------- | ------------------ |
| `start` | Старт и клавиатура раскладов |
| `menu` | Показать клавиатуру снова |
| `help` | Справка и ограничения |
| `last` | Повторить последнее толкование из памяти сессии |

Подробные тексты About/Description — в [BOTFATHER.md](BOTFATHER.md).

## Переменные окружения

Задайте те же переменные, что в [`.env.example`](../.env.example):

- `BOT_TOKEN` (обязательно)
- `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN` (обязательно для ИИ)
- `CLOUDFLARE_AI_MODEL` (опционально) — если не задана, в коде используется **`@cf/meta/llama-3.1-8b-instruct`**. Для ещё более устойчивого русского при большей стоимости и задержке можно задать, например, **`@cf/meta/llama-4-scout-17b-16e-instruct`** или **`@cf/mistralai/mistral-small-3.1-24b-instruct`**; см. [Workers AI Models](https://developers.cloudflare.com/workers-ai/models/).
- `ALLOWED_TELEGRAM_USER_IDS` (опционально) — см. ниже
- `DAY_DRAW_STATE_PATH`, `DAY_DRAW_TIMEZONE` (опционально) — см. раздел «Лимит карты дня»

На платформе: **Secrets** / **Variables**, не файл в образе.

### Whitelist (приглашённые + публичная «карта дня»)

Если задать **`ALLOWED_TELEGRAM_USER_IDS`** (числовой **user id**, не `@username`):

- **Полный доступ** (оба расклада, как раньше) — только у перечисленных id.
- **Остальные пользователи:** команды `/start`, `/menu`, `/help`, `/last` и кнопка **«На день»**; расклад «прошлое — настоящее — будущее» для них **недоступен** (кнопки в интерфейсе не показываются).
- **Пустое значение или отсутствие переменной** — у **всех** полный доступ (две кнопки), как если бы whitelist не использовался.

**Формат id:** через запятую, пробел или `;`. **Неверный формат** при непустой строке — процесс завершится при старте.

**Что сделать вручную:**

1. Узнать **user id** приглашённых (например [@userinfobot](https://t.me/userinfobot)).
2. **Локально / Railway Variables:** `ALLOWED_TELEGRAM_USER_IDS=<id1>,<id2>`, перезапуск сервиса.
3. Проверить: приглашённый видит **две** кнопки; посторонний — только **«На день»** и не открывает spread.
4. Открыть всем полный доступ — **удалить** переменную или оставить пустой.

### Лимит «карта дня» и файл состояния

У **каждого** пользователя карту на день можно вытянуть **не чаще одного раза за календарные сутки** по дате в часовом поясе **`Europe/Moscow`** (настраивается переменной **`DAY_DRAW_TIMEZONE`**, формат IANA). Слот учитывается **после успешной выдачи толкования** от ИИ: сбой генерации не «сжигает» день.

Состояние хранится в JSON-файле (по умолчанию **`data/day-draw-state.json`** в рабочей директории процесса).

- Переопределить путь: **`DAY_DRAW_STATE_PATH`** (абсолютный путь предпочтителен в Docker).
- **Railway / контейнер без тома:** при каждом деплое или смене инстанса файл может **обнуляться** — лимит станет «как в первый раз». Для стабильного лимита подключите **persistent volume** и укажите `DAY_DRAW_STATE_PATH` на смонтированный каталог (например `/data/day-draw-state.json`).
- Один инстанс процесса без общего диска — норма; несколько реплик с **разными** файлами дадут расхождение лимита (при необходимости позже — Redis/БД).

### Команда /last (память процесса)

Последнее толкование хранится **только в памяти** текущего процесса (без БД), с TTL около суток и ограничением длины. После **перезапуска** бота команда **`/last`** ничего не вернёт, пока снова не будет расклада.

**Просроченные callback** у inline-кнопок: Telegram иногда отклоняет `answerCallbackQuery` — бот отвечает на callback без лишнего шума в логах.

## Картинки карт

Файлы **`assets/cards/00.jpg` … `77.jpg`** хранятся в репозитории (десятки МБ), чтобы Docker-образ на Railway сразу содержал изображения без отдельного тома.

Обновить набор: локально `npm run download-cards`, затем коммит.

**Почему раньше предлагали не коммитить:** меньше размер клона и истории Git. Для одного бота и фиксированной колоды коммит проще, чем тома или шаг загрузки при сборке. Если репозиторий станет тяжёлым — можно перейти на [Git LFS](https://git-lfs.com/).

## Сборка образа локально

Из корня репозитория:

```bash
docker build -t vodovorot-bot .
docker run --rm -v vodovorot-day-state:/app/data -e BOT_TOKEN=... -e CLOUDFLARE_ACCOUNT_ID=... -e CLOUDFLARE_API_TOKEN=... -e ALLOWED_TELEGRAM_USER_IDS=123,456 vodovorot-bot
```

## Railway (основной сценарий)

### Чеклист

1. [Railway](https://railway.app/) → **New Project** → **Deploy from GitHub repo** → выбрать `vodovorot-bot`.
2. Сервис должен собираться по **Dockerfile** в корне (при необходимости отключите Nixpacks / укажите Docker).
3. **Variables**: все ключи из `.env.example` (значения только в Railway).
4. **Deployments / Logs**: успешный старт, нет ошибки про отсутствие `BOT_TOKEN`.

### Два способа деплоя при push в `main`

| Способ            | Что сделать                                                                                                                                                |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Встроенный**    | В Railway включён деплой из GitHub: каждый push в `main` собирает репо на стороне Railway.                                                                 |
| **Через Actions** | Workflow [`.github/workflows/deploy-railway.yml`](../.github/workflows/deploy-railway.yml): после **успешного** CI на `main` вызывается `railway up --ci`. |

Используйте **что-то одно**. Если оставить оба, получите **два деплоя** на один push — отключите авто-деплой из GitHub в настройках сервиса Railway **или** не задавайте секрет `RAILWAY_TOKEN` (тогда workflow Deploy Railway будет пропускаться).

### GitHub Actions → Railway

1. В Railway: **Project → Settings → Tokens** (или аналог) → создайте **Project token** для нужного окружения.
2. В GitHub репозитория: **Settings → Secrets and variables → Actions**:
   - **`RAILWAY_TOKEN`** — project token (обязательно для workflow).
   - **`RAILWAY_SERVICE`** — имя сервиса в проекте, если сервисов несколько (опционально).

3. Убедитесь, что в Railway **отключён** дублирующий деплой из GitHub (см. выше), если включили Actions.

Ручной запуск: вкладка **Actions** → **Deploy Railway** → **Run workflow**.

## Fly.io (кратко)

1. [flyctl](https://fly.io/docs/hands-on/install-flyctl/), регистрация.
2. `fly launch`, секреты `fly secrets set ...`, `fly deploy`.
3. Интеграция с GitHub или деплой из Actions — см. [документацию Fly](https://fly.io/docs/).

## Релиз `v1.0.0` (первый тег)

Когда `main` стабилен и CI зелёный:

1. Обновите при необходимости `CHANGELOG.md` и `package.json` (`version`).
2. Коммит, затем:

```bash
git tag v1.0.0
git push origin main
git push origin v1.0.0
```

3. Workflow **Release** создаст GitHub Release (см. [CONTRIBUTING.md](../CONTRIBUTING.md)).
